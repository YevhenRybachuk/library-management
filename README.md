# Library Management

Клієнтський застосунок для управління бібліотекою, реалізований на TypeScript.
Застосунок дозволяє вести облік книг і користувачів, позичати та повертати книги,
видаляти записи, шукати книги за назвою або автором і зберігати дані в LocalStorage.

## Технології

- TypeScript
- Vite
- Bootstrap
- ESLint
- Prettier
- Mocha
- Chai
- Husky

## Запуск проєкту

Встановлення залежностей:

```bash
npm install
```

Запуск dev-сервера:

```bash
npm run start
```

Збірка production-версії:

```bash
npm run build
```

Запуск тестів:

```bash
npm test
```

Перевірка коду лінтером:

```bash
npm run lint
```

Перевірка типів:

```bash
npm run typecheck
```

## Реалізована функціональність

- створення книг;
- створення користувачів;
- видалення книг;
- видалення користувачів;
- пошук книг за назвою або автором;
- позичання книги користувачем;
- повернення книги;
- обмеження до 3 позичених книг на одного користувача;
- повідомлення без використання `alert`;
- модальне вікно для повідомлення про перевищення ліміту;
- збереження книг і користувачів у LocalStorage;
- пагінація списку книг;
- юніт-тести для `Library` та `Validation`;
- pre-commit hook з автоматичним запуском лінтера, перевірки типів і тестів.

## Архітектура

Проєкт розділений за шарами відповідальності:

- `src/models` - класи моделей і TypeScript-інтерфейси;
- `src/services` - бізнес-логіка, generic-клас `Library<T>`, робота зі сховищем і сповіщеннями;
- `src/utils` - допоміжні функції та namespace `Validation`;
- `src/ui` - DOM-компоненти та рендеринг інтерфейсу;
- `tests` - юніт-тести Mocha + Chai.

HTML-файл не містить декларативної розмітки інтерфейсу. Весь UI створюється програмно
засобами DOM API у TypeScript-коді.

## Git workflow

Під час роботи використовувався feature branch workflow. Окремі частини реалізації
виносились у feature-гілки, після чого зміни інтегрувались у головну гілку.

Назви комітів оформлювались за Conventional Commits specification, наприклад:

- `chore: initialize project`
- `build: configure webpack and typescript`
- `feat: add library models and generic library`
- `feat: add library management UI and borrowing`
- `build: migrate from webpack to vite`
- `ci: add github pages deployment`

## Висновок: порівняння webpack та Vite

У межах цього проєкту спочатку була налаштована webpack-версія застосунку, а пізніше
в окремій гілці виконана міграція на Vite. Обидва інструменти дозволяють зібрати
TypeScript SPA, підключити Bootstrap через npm і отримати production-збірку, але на
практиці вони відчутно відрізняються за складністю налаштування та швидкістю роботи.

### Швидкість старту dev-сервера та HMR

Webpack потребує більше часу на старт dev-сервера, оскільки перед запуском він будує
граф залежностей і виконує повнішу підготовку бандла. Для невеликого застосунку різниця
не є критичною, але вона помітна навіть на простому SPA з TypeScript, Bootstrap і кількома
модулями.

Vite стартує швидше, тому що використовує нативні ES-модулі в браузері під час розробки
і не виконує повне бандлення всього застосунку на старті. Для цього проєкту це зручніше:
сервер запускається майже одразу, а зміни в TypeScript-файлах швидко відображаються в
браузері.

HMR у Vite також простіший і швидший у повсякденній роботі. При зміні UI-компонентів,
форм або стилів зворотний зв'язок від dev-сервера відчувається швидше, ніж у webpack.
Для невеликого клієнтського застосунку це робить розробку комфортнішою.

### Час і складність налаштування конфігурації

Webpack потребує детальнішої ручної конфігурації. Для цього проєкту потрібно було
налаштувати:

- `entry`;
- `output`;
- `resolve.extensions`;
- `ts-loader` для TypeScript;
- `style-loader` і `css-loader` для CSS;
- `HtmlWebpackPlugin`;
- `webpack-dev-server`;
- production та development режими.

Такий підхід гнучкий, але для маленького SPA він створює додаткову складність. Потрібно
самостійно знати, які loaders і plugins встановити, як вони пов'язані між собою і як їх
правильно підключити.

Vite потребує значно меншої конфігурації. У цьому проєкті достатньо було створити
`vite.config.mts`, задати `base` для GitHub Pages і налаштувати порт dev-сервера. Обробка
TypeScript і CSS працює з коробки, тому конфігурація стала коротшою і зрозумілішою.

### Розмір і швидкість production-збірки

Webpack створює production-бандл через власний механізм оптимізації. Він добре підходить
для складних застосунків, де потрібен тонкий контроль над chunks, loaders, plugins,
polyfills або нестандартною обробкою ресурсів. Однак для цього проєкту така гнучкість
майже не використовується.

Vite для production-збірки використовує Rollup. У цьому застосунку production build
виконується швидко, а результат залишається компактним: окремо генеруються HTML, CSS і JS
assets. Для невеликого SPA з Bootstrap, TypeScript і DOM-компонентами цього повністю
достатньо.

У практичному сенсі Vite дав простішу і швидшу production-збірку без необхідності вручну
налаштовувати оптимізацію. Webpack також виконує завдання коректно, але потребує більше
конфігураційного коду для такого самого результату.

### Підключення UI-фреймворку та TypeScript

У webpack-версії Bootstrap підключався як npm-залежність і оброблявся через CSS loaders.
Це відповідає вимогам лабораторної роботи, але потребує окремого налаштування
`style-loader` і `css-loader`.

У Vite-версії Bootstrap підключається простим імпортом у TypeScript:

```ts
import "bootstrap/dist/css/bootstrap.min.css";
```

Vite самостійно обробляє CSS-імпорт, тому підключення UI-фреймворку виглядає простіше.
TypeScript також підтримується без окремого `ts-loader`, що зменшує кількість залежностей
і конфігурації.

Для цього проєкту Vite виявився зручнішим саме через мінімальну кількість ручних кроків.
Webpack краще демонструє, як працює класичний bundling pipeline, але для щоденної розробки
простого SPA він є важчим.

### Екосистема плагінів

Webpack має дуже велику й зрілу екосистему. Для складних проєктів це перевага: можна
знайти loaders і plugins майже для будь-якого сценарію. Якщо застосунок потребує складної
обробки assets, legacy browser support, Module Federation або нестандартного pipeline,
webpack залишається сильним інструментом.

Vite також має активну екосистему плагінів, здебільшого побудовану навколо Rollup і
сучасного ESM-підходу. Для невеликих і середніх SPA її більш ніж достатньо. У цьому
проєкті додаткові складні plugins не знадобилися, бо базова підтримка TypeScript, CSS і
dev-сервера вже вбудована.

### Суб'єктивна оцінка для невеликих SPA-проєктів

Для подібного невеликого SPA Vite є зручнішим вибором. Він швидше запускається, має
коротшу конфігурацію, простіше працює з TypeScript і CSS, а також дозволяє менше часу
витрачати на налаштування інфраструктури. Це особливо важливо в навчальному проєкті, де
основна увага має бути на TypeScript, класах, інтерфейсах, generics, DOM-логіці,
валідації, тестах і бізнес-правилах бібліотеки.

Webpack краще підходить як інструмент для розуміння класичної bundler-архітектури та для
великих проєктів зі складними вимогами до збірки. Він гнучкіший, але ця гнучкість має
ціну у вигляді більшої кількості конфігурації та залежностей.

У результаті міграція з webpack на Vite для цього проєкту є виправданою. Функціональність
застосунку залишилась тією самою, але конфігурація стала простішою, dev-сервер працює
швидше, а процес розробки став комфортнішим. Для невеликого клієнтського застосунку
управління бібліотекою Vite є практичнішим і легшим у підтримці рішенням.
